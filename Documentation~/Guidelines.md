# Integration and contribution guidelines

| Concern | Rule |
| --- | --- |
| Application contracts | Define small read-only interfaces on Ghost roots or other root components for query consumers. A Realm initializer creates the root and installs `EntityModule<TData>` instances that turn SDK reports into root state. Consumers use `IGhost.TryGet<T>` for optional contracts or `GetRequired<T>()` for required ones. One root provider per contract. |
| Presence setup | Register `Realm.RegisterPresenceInitializer<TGhost>(kind, ...)` before attaching detectors. For a prefab realm, an enabled `IRealmConfigurator` beneath `RealmSetup` registers initializers before its anchors start. The initializer runs again when reported capability interfaces change, so use `Presence.TryGetModule` before adding a module. With no initializer or module, the Realm still tracks its Presence and Ghost root and ignores SDK payload for which no module exists. An unassigned manifestation blueprint keeps that root viewless. |
| Coordinates | Define units and axes in application contracts. Ordinary sample positions are anchor-local. For large or moving-reference worlds, preserve global doubles in `Double3`, let spatial modules normalize raw SDK inputs to shared Cartesian coordinates and update root `Spatial` components. Use a prefab-configured `RealmSetup` reference frame or a code-configured `Realm.ReferenceFrame`. Projection assigns world poses and handles Anchor parent offsets. See [Spatial](Spatial.md). |
| Spatial ownership | Keep the desired Unity reference near the scene origin and set an appropriate presentation range. Position and orientation are independent channels; articulation can use another application module. Use one root transform writer: remove existing position behaviors from spatial roots, and integrate dynamic physics explicitly. Network scenery should share the same projection; a local cockpit may remain fixed. |
| Ownership | Emas owns the lifetime of Presences, anchors, Ghost roots, installed modules, views and availability. Applications own SDK clients, module types and prefab assets. Each `RealmSetup` owns an isolated realm, while each `AnchorSetup` creates one detector through its colocated `IDetectorProvider`. Anchor manifestation blueprints override realm defaults and leave with the anchor; re-registration refreshes requested views while retaining roots. Detector cleanup unsubscribes but does not dispose a shared client. Dispose query subscriptions and clear retained membership when their consumer stops. |
| Threading and payloads | Call Emas only on Unity's main thread, including detector report/remove callbacks and `Dispatch`. The application owns SDK threading and delivers events on that thread. Copy mutable or reused SDK payloads before publishing because queued callback reports run during a later realm update. Order initial data with live events and undo partial subscriptions if startup throws. Custom detectors must invalidate old callbacks before reattachment. |
| Failure and recovery | Read `LastErrorContext` and `LastError` on the detector; **Window > Emas** shows only the default realm. Set `detector.Name` to distinguish feeds. Detector failure removes its population. Fix the cause, then use `anchor.RestartDetector(detector)` or `ReplaceDetector` to populate it again. Successful restarts or replacements reuse compatible roots and Presences reported during startup handover and remove unreported roots afterward. There is no automatic retry. |
| Disappearance and silent feeds | An explicit disappearance makes a Presence unavailable immediately. Set `detector.DisappearanceGracePeriod` before attachment to retain its inactive root and stable handle for a possible return; zero, the default, removes immediately. `InactivityTimeout` detects feeds that silently stop reporting and follows the same disappearance path. Set a positive timeout longer than the normal publication interval; leave it null for change-only feeds. Every successful report records activity, while direct integrations updating a cached Ghost can call `MarkPublished`. |
| Presentation failures | A view creation or refresh failure removes that view and logs its Ghost and prefab context; tracking stays active. Fix the cause and call `Manifest`, or change the manifestation blueprint, variant or detail to retry. Unchanged reports do not retry automatically. |
| Extension choice | Use one-generic `PollingPresenceDetector<TSource>` or `CallbackPresenceDetector<TSource>` to report SDK entities without creating Ghosts or mapping their state. Subclass `PresenceDetector` when an SDK needs custom lifecycle handling; call `Detect` or `Report<TData>` to pass identity, labels, capabilities and updates to the Realm. Two-generic convenience adapters and protected `GetOrCreate` remain available for direct code integrations. Keep callbacks short and SDK types out of view consumers. |
| Contributions | Use C# 8, Allman braces, XML docs and Unity metadata. Keep runtime independent of editor, sample and SDK assemblies. Cover public behavior with Unity tests, update the changelog, and synchronize shipped samples with `Tests/Unity~/Assets/Samples`. Change version or assembly names only as part of an explicit release decision. |
